# H04 性能基线

## 这份基线为什么不写毫秒

时间基线在别人的机器上必红。CI 的机器、开发容器、谁的笔记本，快慢差着好几倍；
把毫秒数写进断言，等于交付一条对多数人都是红的检查——而一条对谁都红的检查，
很快就会被当成噪音关掉，比没有检查更糟。

所以自动判定只用**结构性的量**：多少条数据，渲染出多少个节点。它在谁的机器上都一样，
而且恰好覆盖这套库里最值钱、又最容易悄悄消失的东西——虚拟化。
虚拟化被顺手去掉之后，页面照样能用、测试照样绿、截图照样对，只是慢十倍，
而「慢」在开发机的假数据上未必看得出来。

原始时间仍然要记，但它属于**记录**而不是断言：跑 `node scripts/check-perf.mjs --record`，
把当次的数字连同环境贴到下面，供人比对趋势。

## 预算与判定

`npm run check:perf`（判据在 `scripts/check-perf.mjs` 的 `BUDGETS`）：

| 入口 | 数据量 | 渲染节点预算 | 这个预算在拦什么 |
| --- | --- | --- | --- |
| `/components/table` | 20000 行 | ≤ 150 | 虚拟化只渲染视口内那几十行；没有它这里会是两万 |
| `/components/layout` | 20000 项 | ≤ 60 | 同上，列表项更轻、窗口更小 |
| `/components/select` | 10000 项 | ≤ 150 | 下拉打开时只渲染可见的那一屏 |

另有整页元素上限 4000，拦的是「某一页把什么都铺出来了」这种整体性退化。

预算**不是按实测值贴着定的**：贴着定的话，任何一次正常的版面调整都会踩线，
于是预算被一路调高，最后失去意义。这里留了三到四倍余量，它要拦的是数量级的变化。
故障注入里有一条专门钉住这件事：预算既不能贴着实测值，也不能松到虚拟化没了还过得去。

还有一条兜底：**渲染出 0 个节点也算失败**。选择器过期之后一个都匹配不到，
`0 <= 预算` 永远成立，检查会一直绿着而其实什么也没在看。
写这份检查时就先踩了一次——虚拟列表的类名猜错，兜底当场拦住。

## 还没做的

- **画布与长消息列表**（`IFlow`、`IChatList`）还没进预算表。它们「渲染了多少」
  取决于视口内的节点数与消息条数，要先想清楚拿什么当那个稳定的量；
  照搬「数 DOM 节点」会把正常的内容增长也算成退化。
- **内存**：`performance.memory` 只有 Chromium 有、还受 GC 时机影响，
  同一页连着量两次能差出三成。要记它就得先定一套「怎么量才算数」的规矩，
  否则记下来的是噪音。
