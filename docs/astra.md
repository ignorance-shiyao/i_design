# i-design：组件体系、业务场景与示例网站实施规划

> 日期：2026-09-13。源码基线：main `62ed38e`。本次实现分支：`feat/astra_redesign`。
> 本文是可拆为 issue/PR 的工程规划；除第 2 节明确列出的本次改动外，所有待办均未在本分支实现。任务优先级、容量和性能预算是建议目标，不代表已测结果或交付承诺。

## 1. 目标与交付边界

让使用者能够完成“发现合适组件 → 理解数据与交互契约 → 调整主题 → 在真实业务页面使用 → 安装到外部项目”的闭环。覆盖对象包括页面布局、表单、表格、各类图标、各类图表、流程图、AI 对话和智能体交互。

采用**共享组件库 + 业务组合层 + 示例应用组 + 全量覆盖实验室**的结构。ERP、OA、分析中心、智能体工作台各自承载自然业务场景；实验室承担少见组件、边界状态和全部主题样式验证。避免为了凑覆盖率将所有组件塞进一个业务页面。

- 范围内：可安装组件、共享逻辑、设计令牌、图标素材与检索、图表与流程能力、页面模板、示例应用、文档、自动生成覆盖报告、测试和版本发布。
- 本轮示例应用阶段范围：可运行前端、确定性 mock 数据、状态迁移、本地持久化、契约适配器与异常注入。真实服务可后接。
- 范围外：完整财务核算/税务合规 ERP、真实企业人事系统、支付、生产审批引擎、自研模型训练、真实外部工具执行、多人实时协作后端。这些需要独立服务与评审，组件库不能承诺具备。
- 保留项目约束：纯色元素填充；图标 + 文字共同表达状态；禁止粗单边线表达类型；`*-solid` 与 `on-*` 配对；图标 SVG/currentColor；共用令牌/图标/纯逻辑；新增库组件按现有多端契约完成适配。
- 本文不假定个人可投入工时。先按依赖与验收拆分，完成首个纵向切片后再用实际耗时估算排期。

## 3. 分层架构与实现顺序

### 3.0 已定：pro 层全端（选项 B）

这是整个规划里最大的前置决策，答案不同 B 组的规模差三到五倍。
**已定为 B：pro 层全端**，与原子组件同样的多端要求，进覆盖矩阵。

`packages/pro-*/` 里是 ProTable / QueryFilter / SchemaForm 这类组合件。
「全端」意味着光 B05（列显隐/排序/宽度/固定/密度/保存视图）就要在
Vue3 / Vue2 / React / 小程序 / Flutter 各做一遍，而这些端对「固定列 +
横向虚拟滚动 + 拖拽改宽」的支持程度差得很远。因此这个决策带三条约束：

1. **先做一个最小 pro 组件的五端垂直切片标定成本**，再排后面的批次。
   切片选 B03 QueryFilter：它是 B 组里最小的 P1，同时已经具备 pro 层的
   全部结构特征——跨端共享的状态机、URL 往返、以及各端差异极大的输入控件。
2. **凡是某端确实做不到的，写成能力声明，不用空壳满足 parity。**
   声明与实现同一次提交，不能等到某个任务卡住了再补。能力差异登记在
   `packages/common/src/contracts/capability.ts`，由 `check:capability` 校验：
   声明里写着「不支持」的组合，那个端就不许存在同名实现文件；
   反过来实现存在却没声明，也算失败。
3. **交互降级要指名替代路径**，而不是「该端暂不支持」一句了事。
   例如小程序没有拖拽改列宽，替代路径是列设置面板里的分档宽度；
   Flutter 没有 URL，替代路径是路由参数对象的同构序列化。

按五端计工作量后，B 组的批次排期随之拉长——这是选 B 的代价，写在这里，
而不是等到某个批次做不完再解释。

```text
现有 packages/common：令牌、图标、数学/格式化/状态逻辑
现有各端包：交互与渲染适配
拟新增业务组合层：ProTable / QueryFilter / SchemaForm / PageState 等
拟新增运行适配层：查询、图表数据、流程存档、AI 事件流
拟新增 examples：ERP / OA / Analytics / Agent Studio / Mobile / Patterns Lab
现有文档站：组件发现、接口、代码、示例入口、覆盖报告
```

建议目录（尚未建立；名称在架构任务完成后固定）：

```text
packages/common/src/contracts/      # 查询、能力声明、图表/流程/AI 契约
packages/common/src/logic/          # 可单测、无框架依赖的 reducer 与校验
packages/common/src/icons/         # 唯一图标源、元数据与生成入口
packages/pro-*/                    # 各端业务组合适配，避免业务逻辑进入原子组件
examples/shared/                   # mock、fixtures、日期/随机种子、权限与持久化
examples/erp/                       # 销售/采购/库存闭环
examples/oa/                        # 审批/组织/协作闭环
examples/analytics/                 # 图表、联动、报告与监控
examples/agent-studio/              # 对话、编排、运行、产物与评测
examples/mobile-workbench/          # 触摸端业务
examples/patterns-lab/              # 注册表自动生成的完整状态与样式覆盖
```

实施原则：先保留现有构建组织方式，通过单个业务切片验证抽象后再拆包；不能一开始迁移全仓。Vue 3 可作为示例应用首个实现，新增**库组件**仍遵守现有多端要求。复杂编辑器在小屏采用列表/属性面板等适配；如果某端确实不支持，必须形成明确能力声明和项目规则修订，不能用空壳满足 parity。

图表保留现有轻量 SVG 为默认路径；高级数据量或复杂图型可评估可选 ECharts 适配包。其 SVG/Canvas 选择取决于数据量和运行环境，必须通过基准测试确定，不将其引入所有基础组件的首屏依赖。[Apache ECharts 渲染器说明](https://echarts.apache.org/handbook/en/best-practices/canvas-vs-svg/)

流程保留当前纯逻辑层与画布，先补端口和校验；只有在正交布线、复杂布局等明确失败用例下再评估独立布局引擎。AI 组件不内置供应商密钥与网络实现，UI 消费统一事件，由应用注入传输适配器。

## 5. 工单拆分规则

优先级：P0 ＝可信接入与基础约束；P1 ＝首个可用业务闭环；P2 ＝广覆盖与高级交互；P3 ＝专门场景。大小 S/M/L 是**相对复杂度**，L 必须在开发前拆成若干可验收 PR，不换算为未经验证的人天。各表“依赖”均指本文任务 ID。

每个任务关闭都应包含：源码/API、文档示例、必要的真实交互测试、明暗/窄屏/减少动效、端适配及生成物更新。任务标记完成需附 PR 和验证结果；不能因为功能名称在目录中出现就勾选。

**ERP 与 OA 不重复实现基础能力**：它们共享人员、组织、审批记录与附件实体。Agent 可以读同一份销售示例数据，提出采购建议并通过同一审批适配器；这让跨站示例证明组件复用，同时保持应用各自可独立启动。

共享到这个程度，ERP 与 OA 更接近「一个应用的两个模块」而不是两个应用。
落地顺序据此定：**先把这两个模块合成一个应用跑通，再按需要拆成两个入口**。
六个示例应用每个都要确定性 mock、状态机、本地持久化与异常注入，
一开始就立六个壳，最可能的结果是六个都停在壳的状态、共享实体各写一份。
拆分的时机是共享层已经被两个模块真实复用过，而不是排期表的第一天。

### 6.2 “全部样式”如何定义和验收

样式集合来自组件的公共 props/variants、主题令牌和状态模型，不能靠人工随手挑几张截图定义“全覆盖”。建立生成数据：

```ts
interface CoverageCase {
  capabilityId: string;
  variant: string;
  state: string;
  platform: string;
  theme: "light" | "dark";
  density: "comfortable" | "compact";
  exampleRoute: string;
  fixtureId: string;
  testId: string;
  availability: "implemented" | "planned" | "unsupported";
  reason?: string;
}
```

覆盖口径：

1. **能力覆盖率**＝存在可运行案例的 implemented 能力 / registry 中 implemented 能力。目标 100%。计划中项单列，不能藏在分母外让读者误以为全量已实现。
2. **状态覆盖率**＝已验证必需状态组合 / 该能力声明的必需状态组合。所有组件覆盖默认/禁用/焦点，异步组件增加 loading/empty/error，动作组件增加确认/冲突/取消。
3. **业务覆盖率**＝被业务任务实际使用的业务能力 / 本里程碑业务能力范围。冷门图型可由 Lab 覆盖，但要明确标注 Lab-only。
4. **端覆盖率**沿用现有矩阵，增加 runtime-verified 与 source-only 区别，避免静态齐全替代真机运行。
5. 主题组合用 pairwise 控制常规回归规模；品牌主按钮、状态标签、图表色阶、确认/危险操作在明暗主题与浅品牌色下逐项全测。

| 验证维度  | 最小集合                                                             | 执行位置                     |
| --------- | -------------------------------------------------------------------- | ---------------------------- |
| 主题      | 亮/暗、默认品牌、浅品牌/高亮色压力样本                               | Lab + 核心业务页             |
| 密度/尺寸 | 舒适/紧凑、组件声明的 size、长中英文/数字                            | Lab + ERP 列表               |
| 视口      | 320、390、768、1440；宽屏分析/画布按需要补                           | Lab + 各应用核心流程         |
| 输入      | 鼠标、键盘、触摸、中文输入法                                         | 表单/菜单/对话/画布          |
| 内容      | 空/单条/大量、长文本/缺字段/非法值/超限                              | fixtures 自动注入            |
| 状态      | 默认、悬停、焦点、选择、禁用、加载、失败、成功、部分成功、过期、取消 | 由能力元数据生成             |
| 权限      | 访客、只读、编辑、审批、管理员；字段/行权限                          | mock 权限策略 + API 契约测试 |
| 动效      | 系统减少动效、站内关闭、正常模式                                     | 既有 motion 检查 + 新交互    |

## 7. 数据模型、状态迁移与接口契约

本节是目标设计，不是当前接口已实现声明。新增契约避免替换现有 props，优先写 adapter。

### 7.1 共用实体

- Organization → User/Membership → Role/Permission；每个记录带 `tenantId`，作用域隔离由服务端落实。
- Product → Warehouse → StockMovement；库存由入/出库流水推导，不能让页面各写一份库存数。
- SalesOrder/PurchaseOrder → OrderLine → Product；金额采用最小货币单位整数和币种，显示格式与计算分离。
- ApprovalInstance → ApprovalTask → ApprovalDecision；关联业务对象、定义版本和审计记录。
- Conversation → Message → MessagePart；Message 支持 parentId/branchId，来源引用关联 SourceDocument/Chunk。
- AgentDefinition → AgentVersion → Run → RunEvent/ToolCall/ArtifactVersion；运行固定版本，工具确认绑定调用与内容摘要。
- Dashboard → Widget → Dataset/QuerySpec；统一时区/单位/聚合与数据更新时间，避免看板卡片统计周期不一致。
- Attachment/Notification/AuditEvent 为共用实体；AuditEvent 只追加，包含 actor/action/object/version/result/time/traceId，敏感字段脱敏。

所有可变实体包含 `id/version/createdAt/updatedAt`；示例约定 UTC ISO 时间存储、界面按明确时区显示。权限矩阵、日期格式、金额格式放共享层；页面不复制规则。

### 7.2 状态机与异常

| 对象     | 主状态                                                                                    | 关键约束/异常                                                       |
| -------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 表单     | pristine → editing → validating → submitting → success/error                              | 失败保留输入；取消只取消当前请求；离开草稿可恢复                    |
| 订单     | draft → pending → approved → fulfilling → completed                                       | pending 可撤回；rejected 回 draft；完成后通过退货单处理，不篡改历史 |
| 审批     | pending → approved/rejected/canceled/expired                                              | 决定绑定 taskVersion；一次有效决定；403/409/410 有明确恢复提示      |
| 数据请求 | idle → loading → ready/empty/error/stale                                                  | 缓存数据刷新失败显示 stale；不同 queryKey 不能共享旧响应            |
| 流程定义 | draft → validating → published → archived                                                 | 发布版本不可直接改写；运行绑定 published version                    |
| AI Run   | queued → connecting → streaming/tool-running/waiting-approval → completed/failed/canceled | cancel/terminal 后不接受正文追加；多工具状态在 ToolCall 单独追踪    |
| ToolCall | pending → running → succeeded/failed；或 pending → awaiting-approval → rejected/expired   | 取消运行不等于外部动作已撤销；适配器必须报告真实结果或未知          |
| 导出     | queued → running → ready/failed/canceled/expired                                          | 下载失效可重新生成；取消幂等；不保留无授权数据文件                  |

### 7.3 API 边界示例

```ts
type PageQuery = {
  cursor?: string;
  pageSize: number;
  sort: { field: string; direction: "asc" | "desc" }[];
  filters: { field: string; operator: string; value: unknown }[];
};
type PageResult<T> = {
  items: T[];
  nextCursor?: string;
  total?: number;
  queryKey: string;
  asOf: string;
  traceId: string;
};
type ApiError = {
  code: string;
  message: string;
  retryable: boolean;
  fieldErrors?: Record<string, string>;
  traceId: string;
};
type RunEvent = {
  eventId: string;
  runId: string;
  sequence: number;
  at: string;
  type:
    | "message.delta"
    | "tool.started"
    | "tool.completed"
    | "approval.required"
    | "artifact.updated"
    | "run.completed"
    | "run.failed"
    | "run.canceled";
  payload: unknown; // 落地时换成各 type 对应的判别联合，禁止 UI 盲读 unknown
};
interface RunTransport {
  start(
    input: unknown,
    options: { signal: AbortSignal; idempotencyKey: string }
  ): AsyncIterable<RunEvent>;
  resume(
    runId: string,
    afterSequence: number,
    signal: AbortSignal
  ): AsyncIterable<RunEvent>;
  cancel(runId: string): Promise<void>;
}
```

| 接口                                 | 请求/输出约束                                         | 失败处理                                |
| ------------------------------------ | ----------------------------------------------------- | --------------------------------------- |
| `GET /orders` 等查询                 | QuerySpec + 明确 page/cursor 方案；total 未知允许省略 | 请求取消、超时重试；不显示伪造总数      |
| `POST /orders`                       | 幂等键 + 已验证 schema；服务端返回规范化对象          | 422 映射字段；重复键返回原结果          |
| `PATCH /orders/:id`                  | expectedVersion/If-Match；权限在服务端检查            | 409 显示差异并要求重新确认              |
| `POST /approval-tasks/:id/decisions` | taskVersion、decision、意见、幂等键                   | 403 不可操作；410 已失效；409 重新加载  |
| `PUT /graphs/:id`                    | schemaVersion、expectedVersion、GraphDocument         | 校验错误定位 node/edge/property         |
| `POST /runs` 与事件订阅              | 配置版本、上下文引用、幂等键、事件游标                | 重连后按 eventId 去重；缺序列可重拉快照 |
| `POST /runs/:id/cancel`              | 请求取消与已取消结果区分                              | 无法撤销的外部动作展示实际/未知状态     |
| `POST /tool-calls/:id/approve`       | toolCallId、版本、动作摘要、过期时间、决定            | 修改动作后旧确认失效；不得静默扩大权限  |

流式协议可以映射到 SSE，`id`/重连相关行为参考 [MDN SSE 说明](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。采用 fetch 流时须自行实现中止/重连解析，不假定等同原生 EventSource。动态表单与工具参数可采用 [JSON Schema 2020-12](https://json-schema.org/draft/2020-12) 描述并独立验证，不能在 UI 中执行 schema 字符串脚本。

### 8.3 灰度和回滚

1. 原子组件保持兼容；新 props 可选，现有默认行为保持，破坏性接口另立迁移任务。
2. 新组合/复杂图表/编辑器通过独立入口和 feature flag 引入；先在示例与 next 版本验证，再进入稳定版。
3. 发布前在干净 checkout 跑检查、pack 消费端、许可证和依赖审计；签入生成物，记录版本与构建 SHA。
4. 文档分支预览沿用现有 `.github/workflows/preview.yml`，main 部署沿用现有链路。示例应用子路径/静态资源路径一并验收。
5. 失败回滚到上一已验证版本；GraphDocument/示例本地存储升级先备份和迁移，旧版不能解释的新 schema 应显示明确提示，不能静默覆盖。
6. 自动发布到注册表、生产数据迁移、真实 AI 工具执行属于后续独立动作；本规划不代表已经执行。

## 9. 推荐实施批次与拆 PR 方法

批次的第一条规则：**第 5 节和第 8 节定义的任务，每一个都必须出现在某一批里**。
这份表是照着任务 ID 全集核过的，H 组的质量任务尤其容易被忘掉——它们不产出
可见界面，但 H01 是 P0。批次内部按第 5 节和第 8 节表里的依赖列排序；
高优先级任务不得排在它所依赖的任务之前（B13/B18/G11 的优先级已按此上调）。

### 第一批：建立可信基线

A01/A02/A04/A05/A08/F01；输出可追溯能力 registry、消费项目与事件协议。完成后可以回答“当前哪些东西确实可用”。A03/A06/A07 按风险继续，避免把所有 SSR/平台扩展都压进第一天。

### 第二批：一条业务链带动组合组件

B01/B02/B03/B04/B08/B09/B12、G01/G02/G03/G11、H05/H01。先让 ERP 订单查、新建、详情、状态变化、失败恢复跑通，再从稳定业务复用点抽取 Pro 组件。新增共享组件按 3.0 定下的 pro 层范围做端适配。
H01 紧跟 G11：覆盖脚本要靠 Patterns Lab 的注册表才能发现演示，G11 一合并就把 H01 接上，别让「新增组件没配演示」这条门槛空置到第五批。

### 第三批：审批和智能体闭环

G05/G08、H08；其依赖 B10/B13/B18/E01 ～ E08/F02 ～ F08/F10 分成独立 PR，顺序按表中依赖。
B13（Markdown/富文本）必须排在 F04（消息渲染）之前——F04 直接消费它；
B18（通知中心）必须排在 G05 之前——G05 的验收里就有「通知」这一步。先用确定性 mock 证明“请求 → 执行 → 确认 → 结果”，再接真实服务。

### 第四批：图表与业务广覆盖

D01 ～ D08/D10/D12/D13、C01 ～ C06、B05 ～ B07/B11/B14 ～ B17、E09/E10、G04/G06/G07/G09/G10、H02/H03。每完成一个图族或页面族，就登记 registry 的样式/状态用例与应用页面。
E09/E10 排在 D08 之后（E09 依赖它）；H02 要等 G03/G05/G08 三条业务链都在，H03 要等 G11 与 A05。
D13 是从 D03 里拆出来的：百分比堆叠、阶梯与目标线都是数据变换，四个端共用一份实现就够；
横条与双轴要动坐标轴本身（轴的方向、第二值轴、单位限制），四端各有一套绘制，
与前者混在一个任务里只会让「做完了吗」说不清。

### 第五批：规模与生态

D09/D11、F09/F11 ～ F15、G12、H04/H06/H07。以实际应用需求决定地图、金融图、语音、多端复杂编辑器的先后，不预设所有能力必须同时落地。
H06（发布渠道与回滚演练）依赖 A03 与 H02，放在这一批收口；它没做完之前不宣称「可发布」。

每个 L 任务建议拆成：① 契约/逻辑+测试，② 默认渲染与交互，③ 异常/无障碍/适配，④ 文档与消费端验证。拆分 PR 可暂存分支，但里程碑完成必须以完整验收为准。

建议下一次任务提示模板：

```text
从 main 最新代码新建分支，实现 docs/astra.md 的 [任务ID]。
先核对源码现状与依赖，禁止重复实现已有能力。
交付：共享逻辑/API、必要的各端适配、文档、真实业务用例、检查结果。
依照 CLAUDE.md 运行现有门槛；不得放宽 parity/a11y/responsive/motion。
完成后回填本任务 PR、验证证据和剩余边界，不勾选尚未实现部分。
```

### 11.4 批次与应用验收路线

1. **先建立核对基线**：J24 的 registry 骨架与 J07/J13/J03 的契约评审。保留现有组件 API，制定扩展与迁移策略。把每项标为 `missing-component`、`missing-capability`、`missing-recipe` 或 `intentional-difference`；发现已实现则附源码和示例证据，不直接删除记录。
2. **ERP 首批**：J01、J06、J07、J13、J19、J23。用“搜索商品 → 新建采购单 → 添加附件 → 查询列表 → 展开/调整列 → 导入失败重试”串起表单、附件、数据表和反馈。
3. **OA 与全局导航**：J02 ～ J05N、J08 ～ J12、J15、J17、J20、J22。用“搜索人员 → 悬停资料 → 发起审批 → 附件预览 → 评论回复 → 通知跳转”串起资料、菜单、消息和弹层。
4. **Agent Studio / Patterns Lab**：J14、J14T、J18、J21；J16 放在门户与商品媒体需要时实施。补齐工具栏、模型选择、专用输入、卡片等配方。任何未被 ERP/OA 使用的变体必须在 Lab 有独立可访问示例，不能因缺少业务入口遗漏。

上述路线是依赖排序，不是额外创建一套与第 9 节冲突的排期。J23 合并进 B04 ～ B07 的同一交付；J22 与 F04/F06 共用消息状态；J01 与 F05 共用附件数据。任务关联多个页面时只实现一次，消费端共享。

### 11.5 每项关闭条件与来源边界

- [ ] 在 registry 留存参考分类 URL、核对日期、本地组件/API、能力列表、示例路由、关联 PR、尚未覆盖状态与差异原因。把参考站仅有静态预览的能力标记清楚，不能宣称其服务端行为。
- [ ] 每个缺失能力分别验收，不能因为新增了一个同名组件就把整分类勾完；对付费/隐藏变体只依据公开可观察内容规划，不复制其源码或受限资产。
- [ ] 公共组件交付共享逻辑及必要端适配、消费端入口、文档与生成物；配方交付可复制组合和真实事件处理。复核浅/深主题、不同密度、320/390px、键盘、无障碍、动效关闭。
- [ ] 业务页面覆盖正常/空/加载/失败/禁用/超长内容；异步类覆盖取消、乱序、重试，涉及选择的组件覆盖受控更新与表单重置。
- [ ] 参考站不提供本任务要求的完整图标、图表、流程编辑器及智能体运行体系的穷尽目录；继续实施 C/D/E/F 系列，不能用本节替代这些既定任务。
