## 1. 现状盘点

### 1.1 架构

一套设计决策落到多个端，令牌、图标、交互算法**只存在一份**：

```
packages/common/src/
  tokens/     设计令牌（编译成 CSS 变量 / Dart 常量 / 小程序 wxss）
  icons/      共享内联 SVG path
  logic/      纯逻辑模块，各端共用（清单见 SOURCE_STATUS）
  styles/     组件样式，只引用语义令牌

src/components/          Vue 3 源头（也是文档站在用的那一份）
  ↓ 脚本转换
packages/vue-next/       Vue 3 发布包
packages/vue/            Vue 2.7（由 Vue 3 源自动转换 + 显式人工清单）
packages/react/          React
packages/miniprogram/    原生小程序自定义组件
packages/flutter/        Dart
packages/mobile-{vue,react}/  复用 Web 组件 + 移动专有形态
```

**这条约定是这个项目最值钱的部分**，改动时别破坏它：算法进 `logic/`，
各端只写渲染适配；任何一端偷偷自己实现一遍，两端就会在某个边界条件上分叉，
而那种分叉不会让构建失败。

**最大的短板**：站点能调**主题**，但调不了**组件参数**。

### 1.6 质量基建

| 检查 | 挡住的问题 |

## 3. 接力约定

### 加一个组件的完整流程

1. **算法进** `packages/common/src/logic/`，纯函数，不碰 DOM
2. **样式进** `packages/common/src/styles/components/`，只引用语义令牌
   （写死色值与尺寸的话，主题面板一调就露馅）
3. **Vue 3 源** `src/components/IXxx.vue` → 跑 `build:vue2` 转 Vue 2 →
   手写 React → 小程序四件套 → Flutter
4. **Dart 期望值由 TS 侧算出**写进 golden test（`packages/flutter/scripts/build-golden-test.mjs`）
5. **文档页** + `src/data/{components,nav}.ts` + 路由
6. `npm run check:parity` 全绿 + **Playwright 实机截图**

### 硬规则（违反即缺陷，哪怕构建全绿）

这三条写在 `CLAUDE.md` 里，这里只提醒最容易踩的：

- **不用加粗/加深的边线表达状态或类型**。状态与类型用「图标 + 淡底色块 + 文字标签」，
  边框保持四边等宽的发丝线。颜色不能是唯一线索
- **元素填充色一律纯色，不用渐变**。纹理与氛围底（点阵、光晕、遮罩、骨架扫光）除外
- **清单类文件一律按目录生成**，手写必然会漏，而且漏掉不会让构建失败
- **中文与中文之间不换行**。模板里的换行会被压成一个空格，中文里那个空格是多的，
  而且真的进了 DOM 文本——复制粘贴带着它，读屏也会读出停顿。要换行就整句写完再换，
  或者让这一行长一点：源码里的一行长，胜过页面上多一个空格。`check:cjk` 会拦

### 「构建通过」不等于「能用」

改了界面就用 Playwright 真跑一遍看截图。本轮就是靠实机截图才发现的：

- Modal 的 watch 没有 `immediate`，命令式对话框挂载时就是打开的，那段逻辑根本不跑——
  Esc 关不掉、背景照样能滚。页面里 `v-model` 切换的用法看不出这个差别
- Scrollbar 的轨道按「需不需要滚动条」`v-show`，而滑块长度要按轨道高度算，
  轨道不在布局里高度就是 0，于是永远算出「不需要」
- CheckTag 的悬停态特指度压过选中态，鼠标停在已选标签上它会变回未选中的样子

### 给 AI 接力的几条

- **先读生成物再读代码**：`componentMatrix.ts` 与 `frameworkStats.ts` 是当前规模的事实
- **不要用 `cat >` 覆盖已存在的文件**。本轮踩过：覆盖 `logic/countdown.ts` 时
  冲掉了移动端 CountDown 依赖的实现。先 `cat` 看一眼再决定是改还是加
- **命令式 API 的宿主不在组件树里**。`message()` / `confirm()` / `notification()`
  挂在 `document.body` 上，inject / context 到不了那里——给它们接上下文要走
  `localeBridge` 那条路，否则接了等于没接，而且看起来像接过了
- **一次一批，做完就合**。每批都要覆盖矩阵不回退、实机验证过、PR 描述写清楚
  「为什么这么做」而不只是「做了什么」

## 4. 交付与审核

这个仓库的协作方式是：**一方按台账实现，另一方审核**。实现者与审核者可能不是同一个
AI，也可能隔了好几天、换了上下文。所以标准写在这里，两边看同一份，而不是各自临场发挥。

### 一轮 = 一个任务 = 一个 PR

不要把台账上的三四项打包成一个 PR。审核者要能一眼看出「这个 PR 想解决哪一条」，
而多项混在一起时，只要有一项不合格，整个 PR 就都得退回——包括那些本来没问题的。

### 硬性门槛（不过就退回，没有商量）

这几条是机器能判的，实现者自己先跑一遍，跑不过别提交：

```bash
npm run check:parity     # 13 项，含跨端一致性与令牌定义
npm run typecheck
npm run build
node scripts/check-theme-readability.mjs
```

外加两条数字上的约束：

- **覆盖矩阵不得回退**。五端的数字必须一致，且不低于改动前
- **golden test 的断言数不得减少**。新增共享逻辑必须补断言——
  少了这一步，Dart 端可以悄悄写出另一套算法而没有任何东西会失败

以及一条不能用机器判、但必须做的：

- **改了界面就要有 Playwright 实机截图**，并在 PR 描述里写出你验证了什么、看到了什么。
  **截图直接拖进 PR 描述，不要提交进仓库**——GitHub 会托管它们。按一轮一个任务算，
  几兆的 PNG 攒十轮就是几十兆，而且进了 git 历史就删不掉（事后删文件也不会让仓库变小）。
  仓库里只留文本证据（例如一份结果 JSON）。
  「构建通过」不等于「能用」：本仓库已经有多次是靠实机截图才发现的问题——
  Modal 的 watch 少了 immediate 导致 Esc 关不掉、Scrollbar 的轨道高度为 0 导致滚动条
  永不出现、样式引用了不存在的令牌导致底色从来没渲染过。这几样构建全都是绿的

### 判断题（审核者会逐条看）

1. **三条视觉禁令**（见 `CLAUDE.md`）：没有用加粗边线表达状态或类型；元素填充是纯色；
   深色底上用浅色文字。颜色不能是唯一线索——状态要同时有图标与文字标签
2. **算法有没有落进 `packages/common/src/logic/`**。某一端自己实现一遍，
   两端就会在某个边界条件上分叉，而那种分叉不会让构建失败
3. **有没有手改生成物**。清单类文件一律按目录生成，见 `HANDOVER.md` 第 3 节
4. **样式有没有只引用语义令牌**。写死色值与尺寸的话，主题面板一调就露馅
5. **注释讲的是「为什么」还是「是什么」**。`// 遍历数组` 这类没有价值；
   要写的是「为什么用向上取整」「为什么这里不能用 v-if」——
   下一个改这段代码的人需要知道的是后者
6. **文档站文案是不是从产品自身视角写的**。不写「对标某某库」，不强调组件数量
7. **PR 描述有没有讲清楚为什么这么做**，而不只是「做了什么」。
   踩过的坑、放弃的方案、实测的数字，这些是这个仓库最值钱的部分

### 退回的判据

有下面任意一条就回炉，不做「先合了再说」：

- 硬性门槛没过，或者根本没跑
- 声称验证过但拿不出实机证据
- 改了生成物、或者把逻辑写死在某一端
- PR 描述与代码对不上（说修了什么，代码里没有）

**判断题不合格不一定退回**——审核者可以直接改掉小问题再合，但要在 PR 里说明改了什么。
改动量大或涉及设计决策的，退回让实现者自己改，避免审核者顺手把别人的思路改成自己的。

### 交接时请给审核者什么

一句话就够：**PR 编号或分支名 + 对应的任务编号**。例如「F0 做完了，PR #29」。

审核者会自己去读 diff、跑校验、必要时起服务实测，不需要实现者复述做了什么——
PR 描述里应该已经写清楚了。
