# H02 第一版业务端到端回归

运行 `npm run check:e2e`。先构建示例，再在随机本地端口提供 `dist-examples`，
Playwright 通过页面操作验证结果。无需开发服务器，不依赖 Vite 源码导入或组件内部状态。
浏览器可用 `CHROMIUM_PATH` 指定；未指定时使用 Playwright 安装的 Chromium。
每个用例独立浏览器上下文，端口与浏览器在失败时也会关闭。

## 范围与结果判据

- ERP：清空明细触发 422，客户输入保留且无创建结果；补全后创建成功；
  重复提交返回同一单号；详情提交到审批中，自己的订单禁止审批且说明理由；
  模拟他人修改后，旧版本不能发货；刷新后发货、关闭；返回列表筛选客户，
  恰好一张订单且最终状态为已关闭。
- Agent：成功、拒绝、取消、失败分别跑正常、乱序、断线重连投递，共 12 种组合。
  确认前无产物；成功后两个版本的付款条款正确；其余结局无产物且显示对应结果；
  工具卡与正文保留；每局重放后的对话结果必须相同。页面运行错误也会判红。
- 权限与版本冲突验证的是页面禁止写入与刷新后恢复操作。
  示例 API 在内存中运行，不能把这两条描述成真实 HTTP 403/409 网络验收。
- OA 尚未实现，H02 保持部分完成；G05 落地后补入申请、审批、退回、通知业务链。

## 故障注入

`scripts/check-e2e.test.mjs` 使用 Playwright 路由修改实际送入浏览器的构建 JS，
工作树不被修改。断言至少发生一次替换，且必须在相应业务断言处失败，避免空注入。

1. 把新订单的 `status:"draft"` 改为 `status:"closed"`：提交动作无法走通，ERP 回归判红。
2. 把 `type:"artifact.emitted"` 改为 `type:"artifact.lost"`：成功局没有报价单，产物预览断言判红。

两项注入均已验证；恢复正常代码后 13 条业务路径通过。

## 本轮发现与修复

原来的乱序窗口跨越了人类确认边界。确认结果先到时，投递循环停止，
确认请求却还在队尾，页面永远没有可点的确认卡。
示例现在分别规划确认前、确认后的投递顺序：人确认后才会产生的事件不能提前跨过边界。
段内仍有确定性乱序，断线恢复仍重发游标事件，由共享 reducer 去重与补齐。

在 Chromium 153、Noto Sans CJK SC 环境对真实构建产物截图与测量：
1440 / 390 / 320 宽度横向溢出均为 0px；
Agent 页面段落实际文本行最长分别为 35.47 / 22.86 / 18.32em。
截图仅用于本次人工查看，不作为跨环境截图基线。
